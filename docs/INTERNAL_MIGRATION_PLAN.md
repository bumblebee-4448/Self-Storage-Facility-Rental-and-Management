# Internal Frontend Migration Plan

## Purpose and evidence

This document records the read-only inventory for migrating the four staff roles from `LeVanThai-Working/self-storage-system-fe`, branch `dev`, into PRM. The source tree inspected was Git tree `3f4877b94194dca13b73acae6f2680eb327294d8`; the related backend controller review used `LeVanThai-Working/self-storage-system-be`, branch `dev`, tree `dc7dab15fc16ded46b6a8fdd69a8908c9f1df810`. The source repository was not cloned into or changed from PRM, and source code is not being copied wholesale.

PRM's starting point is the React 19/Vite application and auth core on `feat/task-05.0-internal-migration`, based on updated `dev`. The customer portal and all existing customer code remain out of this migration.

The legacy repository is a Next.js monorepo. Its `apps/web/app/[locale]` route files mostly compose feature components; its domain API files use the shared Axios client and the workspace package `@self-storage-system-fe/shared`. The inventory below distinguishes what is present in source from whether that behavior or API is safe to carry forward.

## Current PRM boundaries

- `src/api/client.ts`, auth service, refresh coordinator/interceptor, and session-generation code remain authoritative for HTTP and cookie sessions.
- `src/stores/auth-store.ts` remains authoritative for sign-in, sign-out, bootstrap, and invalidation. No legacy auth store, initializer, or token handling is migrated.
- The normalized user exposes the backend-confirmed role as `roles: Role[]`; currently the backend sends one lowercase role string. PRM maps it explicitly and continues to use `permissions: []`.
- `assignedFacilityId` is retained only when validated from the backend. No route, query, or UI may let a user widen their facility scope.
- TanStack Query is used for server-state cache only. Query keys include entity, filters, and facility scope. The app clears query state at identity boundaries so one account's private results cannot remain in another account's view.
- Frontend role checks only control navigation and rendering. They do not establish API authorization.

### Backend authorization blocker

Rechecking the current `dev` controllers shows their `@Security('bearerAuth')` and `@Security('cookieAuth')` decorators commented out, with role authorization left as TODOs. The contract and reservation controllers also contain temporary caller extraction fallbacks. Treat role lists above as intended-policy comments, not enforced authorization. Do not consider FE route guards a security boundary; confirm that BE authentication and role, facility and resource scope checks are enabled before exposing migrated private operations.

## Next.js and monorepo dependencies to remove at the migration boundary

- `apps/web/app/[locale]` file routing, async route params, `next/navigation` redirects/router hooks, and `next/link` are source-only. Use explicit React Router routes and `Link`/`NavLink`/`useNavigate` in PRM.
- Role layouts import `next-intl`; the route layouts call `next-intl/server`. PRM currently has no localization runtime. Keep existing Vietnamese labels for these foundations; add localization only with an agreed PRM-wide decision.
- Contract detail pages unwrap promise-based Next route params with React `use()`. Replace with React Router `useParams()` and validate the identifier.
- Domain features import `@self-storage-system-fe/shared`. Do not add the legacy monorepo or Turborepo to PRM; move only verified types into `src/models/` and `src/api/` as they are migrated.
- Legacy query hooks use `@tanstack/react-query` with the legacy client. PRM has its own QueryClient and cache lifecycle; do not transplant the legacy provider, query defaults, or Axios client.
- Mobile app, landing/customer features, and customer-dependent screens are excluded.

## Target path convention

For each migrated domain, keep page composition separate from domain behavior:

| Concern                                           | PRM path                                                                                |
| ------------------------------------------------- | --------------------------------------------------------------------------------------- |
| App role route page                               | `src/pages/portal/{admin,ops,manager,staff}/...`                                        |
| Shared domain API service                         | `src/api/<domain>-service.ts` using `apiClient` and verified envelope/types             |
| Domain query/mutation hooks and UI                | `src/features/<legacy-domain>/`                                                         |
| Shared backend and UI model types                 | `src/models/<domain>.ts`                                                                |
| Shared page header, table shell, form and dialogs | `src/components/shared/` and only-used `src/components/ui/` primitives                  |
| Route definitions, role defaults and guards       | `src/routes/router.tsx`, `src/config/roles.ts`, `src/components/shared/RouteGuards.tsx` |
| Tests/MSW                                         | `src/test/api/`, `src/test/pages/`, `src/test/routes/`, `src/test/stores/`              |

Feature cache keys must have a stable entity root and include normalized filters plus `facilityId` for scoped lists/details. Successful mutations invalidate only affected entity keys. Mutations remain non-retrying by default. If an endpoint is public, mark its query metadata as public explicitly; session transitions clear the current QueryClient cache before old account data can render.

## Later module migration rules

1. Read the original page, feature components, API, hooks, local types, and shared schema imports.
2. Verify the endpoint and DTO against current BE controller/request/response schemas. Record mismatches before coding.
3. Keep Axios calls in `src/api/` and preserve the shared client, cookies, error normalization, and auth refresh eligibility rules.
4. Keep domain UI/use cases in `src/features/`; page components only compose the module for a role route.
5. Replace Next routes, links, navigation, locale helpers, and async params with React Router equivalents.
6. Use normalized AuthUser data only. Never infer permissions, role grants, or facility scope from a legacy component.
7. Include entity, filters, and facility scope in query keys; invalidate related queries after successful writes.
8. Rebuild with PRM shadcn-compatible components and preserve accessible loading, empty, failure, and confirmation states.
9. Add MSW/RTL tests under `src/test/` using backend-shaped fixtures; do not use old mock data as live production data.
10. Run the complete verification set and review the migration diff before starting another module.

## Missing behavior and open decisions

- BE currently exposes a single role per user and has not confirmed a permission DTO. PRM supports a role array structurally and only normalizes roles the BE actually sends.
- The legacy reservation action API disagrees with the current BE controller as listed above. It is blocked pending the BE contract decision.
- API DTO equality was not proven for all 11 domain modules. Request schemas, response serialization, role scopes, facility filtering, and soft-delete semantics remain module-level verification work.
- The legacy layouts duplicate navigation and use Next locale plumbing; target PRM shell intentionally consolidates them while preserving branding and current session controls.
- Task 05.0 placeholders indicate only that routes exist. They do not imply APIs were called or that business functionality is complete.
